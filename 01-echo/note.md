## 1. そもそもソケットとは

**ソケット = ネットワーク通信のための「口(endpoint)」**。OSが管理する資源で、
アプリからは **ファイルディスクリプタ(fd)= ただの整数** として扱われる。
ファイルと同じように `read` / `write` できるのはこのため。

1つのソケットは次の組で「どの通信か」が決まる:
```
(プロトコル, 自分のIP:ポート, 相手のIP:ポート)
例: (TCP, [::1]:8080, [::1]:52105)
```

`raw/main.go` を動かすと、ソケットが整数(fd)であることがログで見える:
```
待ち受けソケット(fd=3)で :8080 を listen 中
接続受付: 通信ソケット fd=4 (相手=127.0.0.1:52294)
```
→ 待ち受けソケットは fd=3、通信ソケットは fd=4。**別物のソケット**。

---

## 2. 待ち受けソケット vs 通信専用ソケット

役割がまったく違う2種類のソケットがある。

### 待ち受けソケット (listening socket) = `ln`
- 役割:「お店の受付窓口」。新しい接続要求が来るのを待つだけ
- `net.Listen(":8080")` で **1個だけ** 作る
- **データのやり取りはしない**(Read/Writeしない)
- 持っている情報は「自分のポート(:8080)」だけ。相手は未定

### 通信専用ソケット (connection socket) = `conn` / `cfd`
- 役割:「特定の客の専属店員」。1クライアントとだけ会話する
- `Accept()` のたびに **1個ずつ** 作られる
- ここで初めて `Read`/`Write` で実データをやり取り
- 「自分:8080」と「相手:52105」の **両方が埋まっている**

### なぜ分かれているのか
1つの窓口で複数の客を同時にさばくため。窓口は受付に専念し、
実際の会話は客ごとの通信ソケットに任せる。これがコード構造に直結:

```go
ln, _  := net.Listen("tcp", ":8080")  // ① ln = 待ち受け(窓口) 1個だけ
for {
    conn, _ := ln.Accept()            // ② conn = 通信専用 接続ごとに生成
    go handleConn(conn)               //    会話は店員(goroutine)に丸投げ、窓口は次の客へ
}
```

同じ `:8080` でも、`(:8080 ⇄ :52105)` と `(:8080 ⇄ :52107)` は相手が違うので
OSが別の通信として正しく振り分けられる。

---

## 3. それぞれが扱う「情報」

| | 待ち受けソケット | 通信専用ソケット |
|---|---|---|
| アプリが受け取る | `conn`(新しい接続) | 相手が送ったバイト列 |
| アプリが送る | (なし) | 相手へのバイト列 |
| OSが裏で交換 | SYN / SYN+ACK / ACK(接続確立) | データ + seq / ACK(送達確認) |
| 流れるもの | **接続そのもの** | **実データ(バイト列)** |

通信ソケットを流れるのは **純粋なバイト列だけ**。「文字列」でも「メッセージ」でもない。
→ これが 03-protocol で「メッセージの境界は自分で決める」必要が出る理由。

## 4. net.Listen / ln.Accept の正体(自前実装で判明)

`raw/main.go` で `net` の各APIが何を包んでいるか分かった:

| `net` のAPI | 中身(システムコール) | やること |
|---|---|---|
| `net.Listen("tcp", ":8080")` | `socket()` → `bind()` → `listen()` | ①ソケット作成 ②住所割当 ③窓口化 |
| `ln.Accept()` | `accept()` | 確立済み接続を取り出し **新しいfd** を返す |
| `conn.Read(buf)` | `read(cfd, buf)` | 通信ソケットから読む |
| `conn.Write(b)` | `write(cfd, b)` | 通信ソケットへ書く |
| `conn.Close()` | `close(cfd)` | fdを閉じる |

### net.Listen は実は3ステップ
1. **socket()** — まっさらなソケットを作る(まだ住所も役割もない)
2. **bind()** — `:8080` という住所を割り当てる
3. **listen()** — 「このソケットは窓口だ」とOSに宣言。**ここで初めて待ち受けソケットになる**

### ln.Accept の正体
- 引数は **待ち受けソケット lfd**(窓口)
- 戻り値は **新しい通信ソケット cfd**(客ごと)
- 通信ソケットを実際に作るのは **OS**。`accept()` は完成品を取り出して渡すだけ

---

## 5. listen() するとハンドシェイクが自動応答になる

`listen()` を呼んだ瞬間から、そのソケットは接続要求に **アプリ無しで自動応答** する:

```
クライアント                     サーバー(listen済み)
   │   ① SYN          ────────▶ │  OSが受け取り
   │   ◀──────── ② SYN+ACK      │  OSが自動で返す
   │   ③ ACK          ────────▶ │  OSが受け取る → 確立
   │        確立済みキューに積まれる
```

- ハンドシェイクの3往復は **OSが自動**。`accept()` を呼んでいなくても進む
- `accept()` は **確立済みキューから1個取り出すだけ**。ハンドシェイク自体はしていない
- → だから「ハンドシェイク」と「accept」は **非同期**

### キューは2段ある(深掘り)
```
① SYN受信〜ACK待ち  → SYNキュー(incomplete)
        ↓ ACK受信で確立
② 確立済み・accept待ち → acceptキュー(complete)
        ↓ accept()で取り出す
     アプリが通信開始
```
`syscall.Listen(lfd, 128)` の `128` = backlog = 主に **acceptキューの最大長**。
acceptをサボるとここが溢れ、新規接続が受け付けられなくなる。

---

## 5.5 コネクションとソケットは別レイヤー

`accept()` がキューから取り出すのは **コネクション**。それを掴むための
**通信ソケット(fd)を新しく作って返す**。両方関係するが層が違う。

```
キューの中身       : コネクション(OSが管理する接続の状態)
accept()が返すもの : そのコネクションを指す 通信ソケット(fd)
```

| 概念 | 正体 | アプリから |
|---|---|---|
| コネクション | ハンドシェイクで確立した2端点間の通信路。seq/ack・送受信バッファ等の状態としてカーネル内に存在 | 直接触れない |
| ソケット(fd) | そのコネクションを操作するための「取っ手」。カーネル内の状態を指す整数 | read/writeで操作する |

例え:
- **コネクション** = 実際に敷かれた電話線(OSの中にある)
- **ソケット(fd)** = その電話線につながった手元の受話器

`accept()` の瞬間: ①キューから確立済みコネクションを取り出し → ②それを指す
新しい通信ソケット(fd=4)を作り → ③fdをアプリに返す。
→ **取り出されるのはコネクション、返ってくるのはソケット(取っ手)**。

待ち受けソケットとの対比:
| | 指している先(カーネル内) | アプリが持つfd |
|---|---|---|
| 待ち受けソケット `lfd` | 接続を受け付ける窓口の状態 | fd=3 |
| 通信ソケット `cfd` | 確立した1本のコネクション | fd=4 |

どちらも「fd = カーネル内の何かを指す取っ手」で、指す先が違うだけ。

## 6. tcpdump でハンドシェイクを観察

```bash
sudo ./capture-handshake.sh   # 要 root
```

TCPフラグの読み方:
| 表記 | 意味 |
|---|---|
| `[S]` | SYN : 接続したい |
| `[S.]` | SYN+ACK : OK + 受領確認 |
| `[.]` | ACK : 受領確認のみ |
| `[P.]` | PSH+ACK : データ送信(echoのやり取り) |
| `[F.]` | FIN+ACK : 切断したい |
| `[R.]` | RST : 強制切断 |

最初の `[S]` → `[S.]` → `[.]` の3パケットが3ウェイハンドシェイク。
これが `accept()` が `conn` を返す前にOSが裏でやっている部分。
`seq` / `ack` の数字が1ずつ増えてキャッチボールしているのも見える。
末尾の `[F.]` で「切断にもハンドシェイクがある」と分かる。

---

## 結論(ひとことで)

- **ソケット** = OSが管理する通信の口。アプリから見れば fd という整数
- **コネクション** = ハンドシェイクで確立した、2つの端点を結ぶ論理的な通信路。
  通信ソケット(cfd)はその端点をアプリ側で掴むための取っ手
- **net.Listen** = socket+bind+listen の3手で「窓口」を作る
- **ln.Accept** = OSが確立済みにした接続を取り出し、客ごとの通信ソケットを返す
- TCPは **バイトストリーム**。境界は自前で決める(→ 03-protocol へ)
